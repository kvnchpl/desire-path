# Design language

# DESIRE PATH Design Language

This document defines the visual, linguistic, and experiential character of DESIRE PATH.

It is intentionally independent of any particular implementation.

Future redesigns should preserve these principles even if the technology changes.

---

# Philosophy

DESIRE PATH should feel less like using software and more like arriving somewhere.

The interface should encourage orientation rather than operation.

Visitors should feel invited to look, listen, and wander.

The project should remain quiet enough that the encounters themselves occupy the foreground.

---

# Tone

The interface should be:

- calm
- restrained
- spacious
- patient
- attentive
- curious

It should never feel:

- optimized
- gamified
- hurried
- instructional
- performative

The project is not a productivity tool.

It is not a social platform.

It is not a search engine.

---

# Vocabulary

Backend terminology should never leak into the interface unless absolutely necessary.

Use:

Encounter

Path

Place

Time

Feeling

Knowing

Explore

Retrace

Avoid:

Node

Edge

Fragment

Traversal

Graph

Ontology

Epistemology

Distance metric

Nearest neighbor

Composite mode

Backend terminology exists for implementation.

Frontend terminology exists for experience.

---

# Language

Write simply.

Use ordinary words.

Avoid technical explanation.

Prefer:

"Retrace"

over

"Back"

Prefer:

"Explore"

over

"Navigate"

Prefer:

"Near"

over

"Adjacent"

Do not over-explain.

Visitors should discover the logic of the project through use.

---

# Interface

The primary interface should remain minimal.

DESIRE PATH

────────────

Explore

☐ Place

☑ Time

☑ Feeling

☑ Knowing

────────────

Retrace

Avoid adding interface elements unless they significantly improve the experience.

Every new control should justify its existence.

---

# Maps

The map should remain geographically legible.

Encounter locations remain fixed.

Paths change.

The geography should appear stable.

The relationships should remain fluid.

This distinction should remain visually clear.

---

# Motion

Movement should feel gentle.

Prefer:

- fading
- dissolving
- slow panning
- gradual appearance

Avoid:

- sudden jumps
- dramatic zooms
- unnecessary animation
- rapid transitions

Animation should communicate orientation rather than spectacle.

---

# Color

Color should support orientation rather than decoration.

Prefer muted palettes.

Avoid highly saturated interfaces.

Encounters should remain visually primary.

The interface should recede.

---

# Typography

Typography should remain quiet.

Favor readability over expressiveness.

Avoid decorative typefaces.

Allow whitespace to perform much of the visual work.

---

# Paths

Paths represent possibility.

They should feel inviting rather than directive.

The interface should never imply that one path is objectively correct.

---

# Discovery

The visitor should rarely feel completely certain about what lies ahead.

Curiosity should be rewarded.

Prediction should remain incomplete.

The project should preserve a sense of discovery throughout repeated visits.

---

# Opacity

Opacity is intentional.

Not every encounter should be visible.

Not every relationship should be explained.

Absence is part of the cartography.

---

# Complexity

The underlying data model may become sophisticated.

The interface should not.

Complexity belongs beneath the surface.

Simplicity belongs at the surface.

---

# Growth

As the archive grows:

the experience should become richer,

not busier.

New encounters should increase the depth of exploration rather than the density of the interface.

---

# Aesthetic Test

When evaluating a new feature, ask:

Does this make the interface feel more like software,

or more like a landscape?

If the answer is "software,"

reconsider the design.

---

# Final Principle

The visitor should never feel that they are manipulating a database.

They should feel that they are gradually becoming familiar with a landscape.
